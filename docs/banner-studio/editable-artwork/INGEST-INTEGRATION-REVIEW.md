## Accepted boundary

- This validates uploads whose multipart part declares `image/png`. JPEG and WebP remain legacy, with no verified-source metadata. A caller can declare PNG bytes as `image/jpeg` or `image/webp` and take that existing path (`upload.post.ts:25–40`); this is consequently not a universal image-validation or MIME-spoof prevention barrier. That limitation is accepted for this expressly PNG-only increment, not closed by it.
- Supported PNGs are static, noninterlaced, 8-bit color types 0/2/3/4/6, with PLTE/tRNS and fixed-size sRGB/gAMA/cHRM/pHYs metadata as applicable. Unsupported metadata/encodings, including ICC/text/EXIF/APNG, are rejected even when otherwise valid PNG. No color conversion or physical print-size guarantee is added. cHRM is checked for encoded integer bounds and sRGB consistency, not arbitrary color-science validity.
- Bounded validation does not bound total request memory: `readMultipartFormData` still buffers before the file-size check, storage creates a further bounded copy, and later inference/segmentation has its own resource costs. Full R01 ownership, multipart prebuffer limits and production concurrency/CPU headroom remain open.
- The original bytes are retained, not normalized or re-encoded. Processing trusts an upload-validated source only after exact content identity matches. Source integrity is not a proof of extraction quality, editability, print readiness or current user authorization beyond the existing access contracts.

## Findings

**R1 — High, reachable now (admission OFF): string-detected "protected" canvas poisoning causes persistent page-wide denial and an undeletable project.** Detection is substring-based over the whole canvas JSON (`shared/bannerScopedCanvas.ts:4-7`, `shared/bannerDissectionDelivery.ts:33-38`, which percent-decodes). Any detected-but-unparseable reference makes `dependencies()` throw 403 (`scopedCanvasAccess.ts:16-24,48-49`). `projects/upload-banners.post.ts` is unguarded: `requireAuth` only (`:34`), unvalidated `clientId` (`:60-61`), and it writes `uploadBannerAsset(..., fileName, ...)` URLs containing the raw multipart filename (`:98`, key `banner-assets/<user>/<uuid>/<fileName>`, `bannerStorage.ts:134-136`) plus client-supplied `dimensions` in the format key, then INSERTs (`:146`). A filename such as `scoped-banner-exports/x.png` or `a%2Fbanner-studio%2Fdissect%2Fx.png` yields a detected canvas. Consequences: project detail 403 (`projects/[id].get.ts:41`); **the entire project list 403s** for every user whose list includes it (`projects/index.get.ts:80-84`) — admins/owners list across all clients, so one row breaks Banner Studio's project list org-wide; PATCH denies via lineage (`[id].patch.ts:65`), and delete denies (`projects/[id].delete.ts:19-24`), so repair needs manual DB work. Local evidence: running the actual shared detectors via tsx, both URLs above return `detected: true` and `collectScopedCanvasLocators` throws `Malformed protected image reference`; an ordinary URL is not detected. Fix direction: reject protected-looking strings in every remaining canvas writer (at minimum upload-banners, with client access checks), and do not let a malformed/unverifiable row fail other rows — return a redacted placeholder row (no canvas/thumbnail) instead of failing the page. That keeps the "never silently drop after LIMIT" property. Add an authorized repair/delete path for canvases with no parseable dependency.

**R2 — Medium, must close before admission: Dissector import into an existing project skips scoped authority and lineage checks on the existing canvas.** `dissect/[jobId]/import.post.ts:128-143` clones `existing.canvas_data` and assigns `canvasData[targetKey]`. There is no `assertScopedCanvasAccessInTransaction` on the existing canvas and no `assertScopedCanvasLineage(existing, next)`. A write-authorized importer can therefore (a) overwrite a protected format key, erasing its `dissectionSource`/locators without the 409 that PATCH enforces, or (b) once admission is on, add a second uploader's protected source to a protected project. That makes a mixed-uploader canvas that no one can read or delete, which triggers R1/R3 list failure. The fix needs source-first lock ordering: pre-read the target canvas, lock the sorted union of its jobs with this job, then the project. Then recheck unchanged, authorize the existing sources and apply the lineage check.

**R3 — Medium, product/compat activation blocker (current design, not live today):** uploader-only source authority (`scopedCanvasAccess.ts:54`, `dissectionAccess.ts:129`) combined with page-wide list failure (`projects/index.get.ts:80-84`) means that as soon as one protected project exists in a shared client, every colleague assigned to that client, and every admin, loses the whole project list. Separately, the frozen `sessionsInvalidatedAt` (`dissectionAccess.ts:141`) makes the uploader's own protected projects permanently unreadable and undeletable after any session invalidation. The same pattern fails the uploader's whole export history (`exports/index.get.ts:60-69`). Settle this before enabling admission, preferably with redacted placeholders and an owner/admin tombstone-delete path.

**R4 — Low: non-canonical projectId breaks retained delivery.** `RASTER_EXPORT_UUID` is case-insensitive (`exportRendering.ts:8,233`), and provenance stores `projectId: input.projectId` verbatim (`scopedExport.ts:168,181`). Meanwhile the key/row use the lowercased ID (`exportRendering.ts:88,261,281`), and `parseScopedExportProvenance` compares strictly (`scopedExport.ts:96`). An uppercase request therefore creates an export whose download and project export list return 503 permanently, and which cannot be deleted (409). Canonicalize to lowercase (or use `snapshot.target.owner.projectId`) in `prepareScopedExport` and `export-html.post.ts`.

**Compatibility notes (no change requested):** Review-link minting and project delete now use DB-only `resolveDissectionContext` group authority (`links/index.post.ts`, `[id].delete.ts`). Previously they used `requireAuth` only, and other Banner routes use static `roleHasPermission`, so roles whose DB groups diverge from the static map will now get 403. That tightening is intentional but user-visible. Bumps from review submit/respond `updated_at` will 409 a concurrent scoped export (expected stale behavior).
