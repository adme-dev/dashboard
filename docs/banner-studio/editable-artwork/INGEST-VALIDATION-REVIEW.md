# Ingestion validation independent review — 28 October 2026

**Verdict: do not integrate the proposed PNG/JPEG normalizer guard as qualified ingestion validation.** Valid A4 JPEGs are rejected, and accepted large PNGs require several full image buffers. The coordinator accepted both blockers and owns the correction; this review makes no production-source changes, deployment claim, or full R01 acceptance claim.

## Findings

1. **High — valid A4 JPEG regression.** `upload.post.ts` invokes `normaliseArtworkReference(..., 16777216)` before storage, but `artworkValidation.ts:246–256` retains the decoder's 64 MiB accounting limit. Real 2480×3508 JPEGs generated by installed libjpeg-turbo all fail in Node and local workerd: baseline 4:2:0 (470,941 bytes), baseline 4:4:4 (811,330), progressive (338,702), and grayscale (307,068). Direct decoder errors exceed the budget by at least 32, 3, 32, and 11 MiB respectively. All are below the advertised 4096-pixel dimensions, 16,777,216 pixels, and 10 MiB input limit. Endpoint output is HTTP-error status 400 with no storage/DB/dispatch calls. Raising the decoder or runtime limit is not recommended.

2. **High — PNG dimension bounds do not establish a safe runtime allocation budget.** `validateArtworkPng` calls `PNG.sync.read` at line 149. Installed pngjs inflates the entire image, unfilters into another buffer, then constructs RGBA; input copies and parser intermediates add to these allocations. A 75,622-byte 4096×4096 RGBA PNG is accepted: a fresh Node process reports 201,855,629 bytes of array buffers after the handler (~192.5 MiB) and 337,856 KiB peak process RSS (~330 MiB). The 41,915-byte A4 RGBA PNG is accepted with 104,757,994 array-buffer bytes (~99.9 MiB) and ~172.8 MiB peak RSS. These are Node observations, not workerd heap measurements; they demonstrate substantial allocations, not a measured hosted OOM. Local workerd accepts both fixtures, which does not prove production memory or CPU headroom under the application and concurrent requests.

3. **Medium — validation performs an unnecessary JPEG-to-PNG round trip.** Lines 253–256 allocate a PNG buffer, replace it with a copy of decoded RGBA, encode PNG, then fully decode that PNG to validate it. The upload discards the normalized bytes and persists the original. For a valid 1600×1200 4:2:0 JPEG, one instrumented Node run took 239 ms total, including 124 ms in `PNG.sync.write` and 62 ms in `PNG.sync.read`; a subsequent decoder-only run took 47 ms. These are indicative single-run timings, with different warmup, not a controlled benchmark or Workers CPU quota measurement. The 64 MiB jpeg-js accounting limit also excludes JS object overhead and subsequent PNG allocations; it is not an upper bound on request memory.

4. **Medium — helper reuse silently narrows accepted PNG formats.** Valid 16-bit, 1-bit grayscale, Adam7, and fully transparent PNG fixtures are accepted by the raw installed codec but rejected by the new upload guard. The helper intentionally accepts only 8-bit noninterlaced PNGs and requires visible pixels. Rejecting unsupported encodings before allocation is sound, but the user-facing contract must distinguish unsupported encoding from malformed content. Do not remove the Adam7 guard without replacing its unbounded inflation path.

## Required correction and acceptance

Use a dedicated PNG upload validator that streams zlib output through bounded scanline checks without allocating full RGBA or re-encoding. Validate signature, exactly one first IHDR, supported dimensions/bit depth/color type/compression/filter/interlace, chunk bounds/count/order, CRCs, required palette constraints where applicable, contiguous IDAT and a terminal empty IEND with no trailing bytes. Enforce exact expected inflated scanline length and filter-byte range 0–4 incrementally; reject excess output immediately and truncated or invalid zlib termination. Bound input bytes, chunks, streaming buffers and work; cancel/clean up on errors. Do not substitute header-only inspection for decoded-stream validation, and do not merely change `inflateSync` to return another full-size buffer.

Keep JPEG and WebP explicitly on their legacy paths until a separately qualified bounded decoder exists. Do not label their source metadata as decoded-validated; preserving legacy support also means malformed JPEG/WebP rejection is **not** covered by this repair. Retain original-byte storage and validation-before-storage ordering for supported PNGs. State the supported PNG encoding policy rather than silently broadening it.

Before candidate integration, require real A4 RGB/RGBA fixtures, exact-byte retention, malformed/CRC/order/filter/inflation boundary cases, dimension/input-byte rejections, and local workerd evidence using the actual bounded validator. Qualify the maximum supported PNG size and multipart/request-memory behavior separately: `readMultipartFormData` already buffers before the file-size guard. This review does not verify total multipart body limits, production CPU limits, deployed execution, provider acceptance, or full R01 ownership.
