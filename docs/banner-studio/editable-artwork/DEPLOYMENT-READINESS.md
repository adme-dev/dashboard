### Dissector hosted implementation gap

[`queueConsumer.ts::processDissectAnalyze`](../../../server/utils/queueConsumer.ts) currently calls `runDissectionPipeline(null, ...)`. [`bannerDissectorPipeline.ts::downloadFromR2`](../../../server/utils/bannerDissectorPipeline.ts) reads S3 credentials exclusively from `process.env`, falls back to local filesystem if absent, and creates its own S3 client without the fetch handler used by [`storage.ts`](../../../server/utils/storage.ts). [`cfEnv.ts`](../../../server/middleware/cfEnv.ts) caches binding values rather than promoting them into `process.env`. With the configured Pages compatibility behavior, production secret presence therefore does not prove this source download can run. Passing `null` also prevents the Workers AI request-binding fallback; analysis reads `useRuntimeConfig()` for Gemini/Groq.

Before declaring Dissector operational, carry the authenticated internal-request capabilities into the pipeline, use the supported binding-aware/native storage path, resolve provider settings correctly for hosted requests, and test a real queued job. This is a source repair/verification gate, not merely a missing secret. The standalone [`jobs-consumer`](../../../workers/jobs-consumer/DEPLOYMENT.md) already implements the queue-to-HTTP bridge; do not invent a second consumer or rely on the unused Pages Nitro hook. Keep automatic recovery off until this path and its deadline/retry behavior are verified. Core editor release may proceed, but the visible Dissector must not be advertised as working until this gap is closed or unavailable behavior is clearly exposed.
