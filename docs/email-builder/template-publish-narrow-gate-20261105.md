# Separate template publication — 5 November 2026

Source implementation for the approved PRD E07 separation of draft Save and library Publish. This is a subsequent release after workspace PR #832, not an amendment to PR #834. **The new publication gate is false in staging and production; nothing is deployed or hosted-accepted by this work.** Migration 499, template successors, campaigns, modules and global library activation are outside this change.

The existing workspace now offers a separate Publish action only when fresh server discovery grants it. It checks a clean native snapshot and the current saved revision, renders the canonical saved email for desktop/mobile review, shows any server-derived module override paths, and requires explicit confirmation of the new template name/category. Save never publishes. Publication uses the existing `publish-template` request, revision receipt and `edm_templates` owner to create a **new published template ID** while preserving the working draft's ID, head, scope and content. It does not revise a previously published template or change campaigns.

The dialog uses the workspace's Nuxt UI components, semantic colors and typography, bounded preview scrolling, labelled fields and a container-responsive form. Native editing, metadata, reopening and navigation stay blocked during review and from snapshot through publication settlement. Unknown replies retain the original operation ID, CAS and exact payload in the existing roundtrip composable; reconciliation is reachable inside the active modal. A later denial does not erase an uncertain request. If publication commits but its inline readback is denied or fails, the route returns an uncertain 503 rather than a definite 4xx; a failing-first regression proves the original publication remains recoverable. Definite rejection requires another review. The success state is shown only after the exact immutable publication receipt is verified; the original draft remains open.

## Admission and permission matrix

| Boundary | Narrow publication behavior |
| --- | --- |
| Worker rollout | Requires literal `FIGFLOW_EDM_DRAFT_SAVES_ENABLED=true`, `FIGFLOW_EDM_TEMPLATE_PUBLISH_ENABLED=true`, recognized private Worker environment and `pages-auth-me-v1` session authority; no process-env fallback or Pages publication flag. Both checked-in Worker configs and strict deploy expectations keep publish=false. |
| Session and origin | Existing JSON/origin/size/session boundaries apply; expiry, actor mismatch and fresh authority failures stay closed. |
| Agency publisher | Existing fresh ADMIN or MANAGEMENT **and** CREATIVE authority, with existing scope rules, is required at the transaction/readback boundaries. The flag never supplies role or client authority. |
| Ordinary designer / staff / viewer | Assigned CREATIVE alone, marketing rights alone, staff, read-only and revoked authority do not acquire publication rights. |
| Source | Only an existing structured template draft with a current projection and exact expected head; persisted campaign, module and published-template owners are rejected. No implicit initialization or ordinary-draft copy. |
| Allowed command | `publish-template` on the existing templates POST only. `copy-template-draft` and `revise-template` are refused under narrow admission; malformed/forged actor or scope fields fail parsing. |
| Other surfaces | Modules, history, immutable-template GET, brand, conditions and campaign-native authoring stay under their existing independent gates. Existing fully enabled library behavior is preserved, not enabled by this flag. |
| Review / receipt | Internal dependency reads reuse existing module helpers; they do not open module routes. The narrow POST returns its exact immutable readback, so the client does not need broader library GET/history admission. |
| Concurrency | Existing transaction/receipt owner preserves one commit for matching retries, rejects changed-payload operation reuse and stale new operations, and rechecks fresh publisher/read authority. |
| Publication / delivery | Existing asset, dependency and rendering checks remain authoritative. No image publication, template successor, campaign send, customer email, provider change or migration 499 is performed. |
