## Smallest missing links and next slices

1. **Connect the campaign to the existing job/task.** Add an optional, server-validated work reference on the existing campaign draft contract and readback, using `projectId` as the job owner and an optional `taskId` only where needed. Derive/validate brief linkage from the task/project conversion rather than requiring staff to re-enter every ID. Reject cross-client, mismatched task/project and unauthorized board references. Carry the association through existing create/edit UI and the existing MCP create/read operations; provide a task-to-campaign link and read-only delivery status. No new workflow/run table, automatic task closure, approval shortcut or dispatch trigger. Acceptance: reopen the job/task and find the same campaign; cross-client references fail; draft association changes cannot alter an approved send silently.

2. **Make template selection name an exact revision.** Extend existing audience/template discovery to return the authorized canonical document/revision and completeness status, then extend campaign creation to select that exact revision. Reuse the current immutable template read/copy owner and renderer after the parent's library integration passes; retain pins, policy, client rebinding rules and provenance. Keep legacy templates compatible. Do not expose arbitrary canvas/native commands, invent a second library, or couple this to general MCP design editing. Acceptance: changing a template head after selection cannot change the created campaign's selected content; stale/foreign revisions fail or require explicit reselection; the resulting campaign uses the unchanged propose/review/execute flow. The MCP draft hash and UUID design revision are different tokens and must remain explicit.

3. **Expose just enough brief/job-budget context to finish the work.** Existing department brief reads are summaries; `get_briefs` is also a summary and is not a safe substitute for assigned-client detail. First expose authorized field responses and current linked project/task references through the existing brief service/read family, excluding contacts/accounting/private metadata. Add read-only linked proposed job allocations with clear `proposed` state and missing-write warnings; do not label them approved budgets or reuse `media_spend` IDs. Where AM confirmation/editing is required, complete only the existing job-allocation/change-log model and existing budget surface, with explicit period/month, author/reason and stale-value protection. Keep provider budget writes and finance outside this slice. Acceptance: one known job shows the actual brief, deadline, allocation units/period/state and provenance; missing allocation data stays visibly missing after nonfatal conversion failure. Do not build a second budgeting engine merely to provide context.

4. **Qualify the connected journey through existing gates.** Preserve the parent core bridge gate and current F/M ledger; references/MCP work should not delay or take over native integration. After the accepted source is integrated/released, record actual employee OAuth/catalog parity and perform a synthetic no-send path from scoped work discovery to linked draft, selected revision, audience, stale-review denial and provider-disabled refusal. Only separately authorized test delivery establishes transport; Apple Mail/Gmail/Outlook acceptance remains the FigFlow real-client gate. A focused source-backed amendment to the existing workflow PRD/MCP roadmap is enough; avoid another master PRD or orchestration roadmap.

There is no demonstrated need for a new staff-management MCP write, general project-conversion tool, scheduler, automatic budget synchronizer or file-transfer tool for this journey. Existing application decisions can remain visible handoffs until a specific approved MCP use case requires them.
