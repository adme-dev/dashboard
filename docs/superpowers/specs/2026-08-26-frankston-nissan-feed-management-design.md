# Design — Frankston Nissan catalogue feed management

**Date:** 2026-08-26 · **Status:** design (awaiting written-spec review) · **Owner:** agent build

**Source brief:** `/Users/paulgiurin/Downloads/frankston-nissan-feed-brief.md`

**Implementation bases:** XeroFlow `main` at `66e9f1c8`; Social Dashboard `main` as inspected on 2026-08-26

## 1. Outcome

Frankston Nissan's Meta vehicle catalogue will be generated by Social Dashboard, registered under Frankston Motor
Group in XeroFlow, and observable through the existing feed MCP tools. The live Meta catalogue remains
`952157521953514` and the existing Meta product feed remains `638660590098129`; the work must update and bind that
feed rather than create a duplicate.

The completed flow will:

- generate iMotor vehicle links with the stable short-link contract
  `https://www.frankstonnissan.com.au/{condition}-cars/for-sale/{stock_number}`;
- exclude and count unpriced or imageless vehicles before XML generation;
- preserve both new and demonstrator stock until the media team makes an explicit demo-policy decision;
- resolve `Frankston Nissan` as an alias of Frankston Motor Group
  (`8b45925c-bc32-4b7c-afc1-cfc46d81c9dd`);
- expose item totals, `byCondition`, and exclusion reasons through `get_inventory_feed_health`;
- prepare a confirmation-gated proposal that reuses Meta product feed `638660590098129`;
- verify every operational write by re-reading state through the MCP transport; and
- use the same safe registration path for Peter Davey Suzuki, without guessing missing identities.

No deployment, Meta mutation, or production database write is implied by merging code. Operational changes remain
separate, auditable steps.

## 2. Current-state findings

### 2.1 Live feed and inventory evidence

The current Meta product feed schedule points to the legacy Netlify generator:

```text
https://adme-facebook.netlify.app/facebook-frankston-nissan.xml
```

The legacy generator reads iMotor-style inventory JSON and guesses a URL by matching a model/year/badge prefix
against `sitemap-stock.xml`. Multiple vehicles can share that prefix, so the final match can be a variant or another
vehicle. The current public inventory record does not contain a canonical URL field; therefore the source brief's
assumption that a canonical URL can simply be copied from that record is not valid for this source.

iMotor provides a dealer-specific short-link resolver. Live checks on 2026-08-26 proved both supported conditions:

```text
/new-cars/for-sale/3000569
  -> /new-cars/for-sale/nissan/patrol/2026/warrior/y62-my26-4x4-dual-range/3960404/

/demo-cars/for-sale/2993335
  -> /demo-cars/for-sale/nissan/navara/2026/st/d27-my26-4x4-dual-range/3917475/
```

Social Dashboard already exposes this exact iMotor preset:

```text
https://{domain}/{condition}-cars/for-sale/{stock_number}
```

The design uses that contract and removes the legacy sitemap-prefix selection from the managed feed path.

### 2.2 XeroFlow registry state

Production read-only inspection found:

- canonical client: Frankston Motor Group (`8b45925c-bc32-4b7c-afc1-cfc46d81c9dd`);
- no `Frankston Nissan` client alias;
- no Frankston Motor Group dealer/feed link;
- an active Frankston Nissan Meta connection
  (`a864afee-99c4-4815-81ef-e0bb7577173e`, ad account `793271381442835`);
- no Frankston Motor Group Meta catalogue binding; and
- no current XeroFlow path that deliberately selects an existing Meta product feed by ID during attachment.

`ensureMetaCatalogFeed` currently reuses a feed only when its schedule URL already equals the XeroFlow serve URL.
Because `638660590098129` still points to Netlify, an attachment today would create a duplicate. This must be fixed
before any live proposal is confirmed.

## 3. Architecture

### 3.1 Social Dashboard owns feed generation

Create or upsert a Facebook vehicle feed for the Frankston Nissan seller scope in Social Dashboard. The feed uses:

```json
{
  "website_domain": "www.frankstonnissan.com.au",
  "link_template": "https://{domain}/{condition}-cars/for-sale/{stock_number}",
  "currency": "AUD"
}
```

The source is constrained to the existing Frankston Nissan seller reference
`429f65c8-69ab-44c9-6243-c7fd59e86eb6`. The dealer link repeats that seller scope so XeroFlow preview requests
cannot broaden the inventory query to another Frankston Motor Group franchise.

The iMotor short URL is the emitted item URL. It is stable across changes to make/model/year/badge slugs and resolves
to the vehicle detail page. Social Dashboard must not use the legacy sitemap-prefix algorithm or synthesize a
variant URL.

### 3.2 Saleability and exclusion evidence

Social Dashboard's public serve path already validates rows before XML generation and reports validation summaries.
The Facebook validator will be aligned with the existing Google validator so price must be numeric and greater than
zero. A missing or zero price produces a `price` issue; a missing image produces an `images` issue. Both rows are
omitted from the XML while remaining visible in validation counts.

URL construction requires non-empty `condition` and `stock_number` values. For the iMotor template, an unresolved
placeholder or an unsupported condition is an invalid URL and must be reported as a `url` issue rather than emitted.
Supported condition paths are `new`, `demo`, and `used`.

The feed health response groups provider validation issues into the existing stable contract:

```text
excluded.invalidListingUrl
excluded.missingPrice
excluded.missingImage
excluded.other
excluded.totalExcluded
```

No minimum-price filter is used to hide bad rows before validation; doing so would make the exclusion count
dishonest. Validation sees the complete seller-scoped candidate set and performs the exclusion.

### 3.3 Demo policy remains observational

No `condition` filter will be applied during this round. The served feed can include new, demo, and used records when
the dealer source supplies them. XeroFlow computes `byCondition` from served items and always returns explicit
`new`, `demo`, and `used` keys, including zero values.

This gives Alicia the evidence needed to decide whether the New Cars campaign should include demonstrators. A later
product-set change must use `propose_set_product_set_rules` and its item-count preview; it is not part of this work.

### 3.4 XeroFlow client and dealer registration

An additive, idempotent migration inserts the normalized alias `Frankston Nissan` for Frankston Motor Group. The
alias uses the existing `agency_client_aliases` uniqueness and normalization conventions. Name resolution must return
the canonical Frankston Motor Group client while preserving the requested alias in user-facing context where the
current resolver does so.

The dealer link is created through the existing feed administration boundary, not by bypassing it with an ad-hoc
row. It binds:

- XeroFlow client ID `8b45925c-bc32-4b7c-afc1-cfc46d81c9dd`;
- the verified Social Dashboard organization;
- seller reference `429f65c8-69ab-44c9-6243-c7fd59e86eb6`; and
- the created/upserted Frankston Nissan feed as the default feed.

The link write is followed by `get_inventory_feed_health` over MCP. Direct database inspection can support diagnosis
but cannot satisfy acceptance.

### 3.5 Existing Meta product-feed selection

The catalogue-attachment contract gains an optional `productFeedId`. When supplied:

1. list the feeds accessible under the requested vehicle catalogue;
2. require an exact ID match inside that catalogue;
3. show the selected feed's current name and schedule URL in the dry-run proposal;
4. preserve the normal confirmation token and `confirm_action` gate;
5. after confirmation, update that feed's name and schedule to the XeroFlow serve URL;
6. request a Meta upload;
7. read the feed back and verify ID, URL, interval, timezone, the hour when the interval is daily, and upload
   identity; and
8. persist the binding evidence only after all readback checks pass.

If the supplied ID is absent from the catalogue, the operation fails closed. It never falls back to creating a new
feed. The existing URL-match/create behavior remains available only when callers omit `productFeedId`, preserving
backward compatibility for new registrations.

For Frankston Nissan, the dry-run request must name:

```text
catalogId: 952157521953514
productFeedId: 638660590098129
schedule: { interval: HOURLY, timezone: Australia/Sydney }
```

The explicit schedule retains the live feed's hourly cadence instead of applying XeroFlow's default daily schedule.
The proposal is presented to Paul and execution stops until Paul explicitly confirms it. Owner god-mode does not
bypass this gate.

### 3.6 Peter Davey Suzuki

Peter Davey Suzuki follows the same dealer-link and existing-product-feed selection path. Before a proposal is
created, live read-only state must prove its canonical client, Social Dashboard organization/feed, Meta connection,
catalogue ID, and product-feed ID. If any identity cannot be proved, the Peter Davey portion is reported as blocked
with the missing evidence; no inferred ID, duplicate feed, or direct database binding is permitted.

## 4. Interfaces and compatibility

### 4.1 Meta platform input

The platform-level input becomes:

```ts
interface EnsureMetaCatalogFeedInput {
  // existing fields unchanged
  productFeedId?: string
}
```

When `productFeedId` is present, the result continues to report `feedDisposition: 'reused'`. No new disposition is
required because downstream code already interprets `reused` as an existing feed that was updated.

### 4.2 MCP proposal input and preview

`propose_attach_catalog_feed` accepts optional `productFeedId`. Its preview includes:

```ts
{
  catalogId: string
  existingProductFeedId: string | null
  existingProductFeedName: string | null
  currentScheduleUrl: string | null
  proposedScheduleUrl: string
  willCreateProductFeed: boolean
}
```

For an explicitly selected existing feed, `willCreateProductFeed` is always `false`. The confirmed payload is bound
to the previewed IDs and schedule so a changed confirmation request cannot substitute another feed.

### 4.3 Feed health

No new MCP tool is introduced. `get_inventory_feed_health` remains the read surface and returns:

```ts
{
  itemCount: number
  byCondition: Record<string, number>
  excluded: {
    invalidListingUrl: number | null
    missingPrice: number | null
    missingImage: number | null
    other: number | null
    totalExcluded: number | null
  }
  catalogBinding: {
    catalogId: string
    productFeedId: string
    state: string
  } | null
}
```

Null exclusion values mean the provider returned no validation metadata. Zero means validation ran and found none.
That distinction is preserved.

3. Fetch the public serve URL and audit URLs, prices, images, exclusion counts, and condition totals.

5. Apply the alias migration automatically to the configured Neon database after its tests pass.
6. Create the dealer/feed link and verify feed health over MCP.
7. Produce the Frankston Nissan Meta attachment dry-run targeting `638660590098129` and stop for explicit approval.
8. After approval, execute, then re-read feed health, Meta binding, product-feed schedule/upload, and campaign ad

9. Resolve Peter Davey Suzuki identities and repeat the link/proposal/readback workflow, retaining the same explicit

The Social Dashboard and XeroFlow code changes are developed in separate isolated worktrees and separate branches.
No branch switching or edits occur in the user's active dashboard checkout.

## 6. Test and acceptance plan

Implementation is test-driven and covers:

1. Facebook validation rejects empty, non-numeric, negative, and zero prices while accepting a positive price;
2. the iMotor template emits `new`, `demo`, and `used` short links from normalized condition and stock number;
3. unresolved placeholders or unsupported conditions are classified as URL failures;
4. the public serve path omits invalid rows and returns an honest invalid-item count;
5. `Frankston Nissan` resolves to Frankston Motor Group without affecting other aliases;
6. an explicit Meta product-feed ID is reused even when its current schedule URL differs;
7. an explicit ID outside the selected catalogue fails without calling create/update/upload;
8. omission of `productFeedId` preserves URL-match and create behavior;
9. the proposal preview exposes the existing feed and creation intent before confirmation;
10. confirmed execution reuses the previewed ID, reads it back, and persists evidence only after verification; and
11. MCP feed health returns reconciled `itemCount`, `byCondition`, and exclusion categories.

Live acceptance for Frankston Nissan requires:

- every emitted URL uses the iMotor short-link shape and ends in the source stock ID;
- sampled new and demo URLs resolve to a vehicle detail page, not `/our-stock/` or a model/variant page;
- no emitted price is empty, non-numeric, negative, or zero;
- every emitted item has at least one image;
- served count plus excluded count reconciles with the seller-scoped candidate count;
- `byCondition` reconciles with the served count;
- the XeroFlow binding reads back catalogue `952157521953514` and product feed `638660590098129`;
- `get_ad_product_set_bindings` for campaign `120231259100460027` returns ads with explicit `bindingIntact`; and
- `propose_refresh_catalog_feed` can preview a confirmation-gated refresh for the registered feed.

## 7. Safety and rollback

- Social Dashboard continues serving the new URL independently before Meta is repointed.
- Meta is not changed until the new serve URL passes the live audit and Paul confirms the exact proposal.
- Explicit product-feed selection fails closed, preventing duplicate creation.
- The legacy Netlify URL remains available as a rollback schedule target during the transition.
- The client alias migration is additive and idempotent; it does not create another agency client.
- Dealer links and Meta binding evidence are auditable registry records and can be disabled without deleting feed
  history.
- No product-set filtering or campaign targeting changes are included.

## 8. Non-goals

- rewriting or deleting the legacy `facebook-feeds` repository;
- changing the Frankston Nissan campaign's demo policy;
- modifying a Meta product set filter;
- creating a new Meta catalogue or product feed;
- changing ads, budgets, creative, audiences, or campaign status;
- deploying either application without a separate deployment authorization; or
- treating direct database inspection as operational acceptance.
